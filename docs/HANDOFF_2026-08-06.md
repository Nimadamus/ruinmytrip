## 3. Why the rotation stopped

The rescue workflow `.github/workflows/backup-reencrypt-once.yml` exists on the feature branch
(7839 bytes) but **cannot be dispatched**. GitHub only registers `workflow_dispatch` workflows that
are present on the **default branch**. The Actions API lists only:

```
db-backup      [active]  .github/workflows/db-backup.yml
render-deploy  [active]  .github/workflows/render-deploy.yml
weekly-digest  [active]  .github/workflows/weekly-digest.yml
```

Putting the file on `main` would push to `main`, which deploys production. That is not permitted, so
the rescue is blocked pending a decision.

The rescue exists because GitHub stores one value per secret name and overwriting is irreversible:
rotating `BACKUP_PASSPHRASE` without first re-encrypting would strand every existing artifact.

## 4. The decision needed to resume

Choose **A**, **B**, or **C**. Nothing else is blocked.

**Option A — temporarily change the default branch** *(was the recommendation)*
```
gh repo edit Nimadamus/ruinmytrip --default-branch feature/travel-warning-platform
gh workflow run backup-reencrypt-once.yml --ref feature/travel-warning-platform \
  -f source_run_id=31100989871 -f artifact_name=rmt-db-backup-20260806T122135Z
gh repo edit Nimadamus/ruinmytrip --default-branch main
```
No commit or push to `main`, so no deploy fires. Reversible in one command.
Cost: the default branch is briefly wrong; an interruption mid-way leaves it that way until fixed.

**Option B — disable the deploy workflow, push the rescue workflow to `main`, re-enable**
```
gh workflow disable render-deploy.yml --repo Nimadamus/ruinmytrip
# push .github/workflows/backup-reencrypt-once.yml to main, dispatch, then:
gh workflow enable render-deploy.yml --repo Nimadamus/ruinmytrip
```
Leaves a real commit on `main`. More invasive than A.

**Option C — skip the rescue entirely**
Rotate now and let the old artifacts age out over their 30-day retention.
Less costly than it sounds: the very next step creates a fresh backup under the new passphrase, so
there is never a moment without a current, human-recoverable backup. What is lost is up to 30 days
of *history*, not the current state.

### After the decision, the remaining sequence

1. (A or B only) Run the rescue workflow; record run ID, artifact name, size, timestamp, checksum.
2. Download the re-encrypted artifact; decrypt locally using the DPAPI blob — **no Pinentry needed**,
   `gpg --batch --pinentry-mode loopback --passphrase-fd 0`, fed from the redirected process.
3. Restore into a disposable PostgreSQL 16 and run integrity checks (table count, migration level,
   destination count).
4. Only if that passes: set `BACKUP_PASSPHRASE` to the new value via the same stdin method.
5. Run a fresh production backup (`gh workflow run db-backup.yml`), download, decrypt, restore, check.
6. Delete `BACKUP_PASSPHRASE_NEXT` **only after both restores pass**.
7. Confirm the DB firewall is re-locked (`ipAllowList: null`).
